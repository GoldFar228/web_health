При этом многие решения закрыты, ориентированы преимущественно на мобильные устройства, ограничены платными функциями или не позволяют гибко адаптировать систему под индивидуальные сценарии.

В отличие от бумажных записей и электронных таблиц, веб-приложение может автоматически выполнять расчеты, хранить историю действий, обеспечивать быстрый поиск данных, защищать пользовательский доступ и предоставлять единый интерфейс для работы с тренировками и рационом.

Практическая потребность в подобном программном продукте возникает как у самостоятельных пользователей, так и у специалистов фитнес-индустрии. Пользователю важно видеть план тренировок, фактические подходы, повторения и нагрузку, а также понимать, сколько калорий и макронутриентов было потреблено за день. Для тренера или разработчика системы важно иметь расширяемую платформу, которую можно дополнять модулями рекомендаций, аналитики, расписаний и коммуникации с клиентами.

# 1 Методы разработки веб-приложения для учета тренировок и питания пользователя

## 1.1 Характеристика предметной области

Контроль физической активности и питания связан с постоянным накоплением небольших, но важных данных: дата тренировки, состав упражнений, количество подходов, рабочий вес, длительность занятия, калорийность приема пищи, количество белков, жиров и углеводов. Если такие данные хранятся разрозненно, пользователь быстро теряет целостную картину своего прогресса.

Традиционные способы учета, такие как бумажный дневник или таблицы, обладают низкой степенью автоматизации. Пользователь вынужден вручную рассчитывать суммарные показатели, повторно вводить одинаковые продукты и упражнения, самостоятельно искать справочную информацию. При длительном использовании такие подходы приводят к ошибкам, дублированию записей и снижению мотивации.

Особенность предметной области состоит в необходимости сочетать персональные данные, пользовательский ввод и справочную информацию из внешних источников. Например, данные о продукте могут быть получены из внешней базы FatSecret, а информация об упражнениях - из сервиса Wger. При этом итоговые записи должны принадлежать конкретному пользователю и храниться в локальной базе приложения.

Современные инструменты для мониторинга здоровья можно разделить на несколько категорий в зависимости от их назначения и функциональных возможностей.

Персональные трекеры активности - устройства и приложения, фокусирующиеся на подсчёте шагов, измерении пульса, отслеживании сна. Примеры: Fitbit, Garmin Connect, Apple Health. Основные характеристики:

автоматический сбор данных с датчиков;

минимальное участие пользователя в процессе ввода информации;

интеграция с экосистемой производителя.

Платформы для управления тренировками - решения, позволяющие составлять планы занятий, фиксировать выполненные упражнения, отслеживать прогресс в силовых показателях. Примеры: Strong, JEFIT, Hevy. Ключевые особенности:

библиотеки упражнений с инструкциями;

возможность создания персональных программ;

статистика по выполненным подходам и весам.

Сервисы учёта питания - приложения для подсчёта калорий и макронутриентов. Примеры: MyFitnessPal, FatSecret, Yazio. Функциональные возможности:

базы продуктов с пищевой ценностью;

сканеры штрих-кодов;

дневники приёмов пищи;

расчёт рекомендуемой нормы калорий.

Комплексные платформы - системы, объединяющие несколько направлений мониторинга. Примеры: Google Fit, Samsung Health, Cronometer. Преимущества:

единая точка доступа ко всем данным о здоровье;

кросс-платформенная синхронизация;

расширенная аналитика.

Разрабатываемое решение web_health относится к категории комплексных платформ с акцентом на веб-интерфейс и возможность кастомизации под индивидуальные потребности (рисунок 1).

Таким образом, проведённая классификация позволяет выделить основные функциональные блоки, которые должны быть реализованы в разрабатываемом веб-сервисе: учёт тренировок, контроль питания, аналитика прогресса. Это послужило основой для последующего сравнительного анализа существующих решений.

## 1.2 Анализ существующих решений

На рынке цифровых фитнес-сервисов можно выделить несколько групп решений. Первая группа - приложения для трекинга активности и здоровья, такие как Apple Health, Google Fit и Garmin Connect. Они хорошо работают с данными устройств и датчиков, но не всегда удобны для ручного планирования тренировок и детального учета питания.

Вторая группа - приложения для учета питания, например FatSecret, MyFitnessPal и аналогичные калорийные дневники. Их сильной стороной является большая база продуктов и автоматический расчет калорийности. Недостатком для рассматриваемой задачи является то, что тренировки обычно представлены как дополнительная функция, а не как полноценный модуль планирования и анализа.

Третья группа - приложения для силовых тренировок и спортивных дневников. Они позволяют фиксировать упражнения, подходы, повторения и вес, однако не всегда имеют развитый модуль питания и не всегда позволяют свободно адаптировать структуру данных.

Для определения требований к разрабатываемой системе был проведён анализ пяти популярных решений. Результаты представлены в таблице 1.

В ходе исследования были идентифицированы следующие недостатки актуальных продуктов:

зависимость от конкретного производителя устройств (Apple Health работает преимущественно с экосистемой Apple);

ограничение функционала в бесплатных версиях (MyFitnessPal скрывает детальную аналитику за подпиской);

отсутствие возможности самостоятельного развёртывания (все данные хранятся на серверах компании);

недостаточная гибкость настройки под специфические потребности (например, для пауэрлифтинга или кето-диеты);

проблемы с конфиденциальностью персональных данных о здоровье.

Разработка собственного решения позволяет устранить перечисленные ограничения и предоставить пользователям полный контроль над своими данными.

Анализ таблицы показывает, что существующие решения либо специализируются на одном направлении (только питание или только тренировки), либо требуют оплаты для доступа к расширенным функциям. Разрабатываемое приложение позиционируется как бесплатная альтернатива с открытой архитектурой.

## 1.3 Требования к разрабатываемой системе

### 1.3.1 Функциональные требования

Функциональные требования определяют действия, которые пользователь должен иметь возможность выполнять в системе. Для приложения web_health такие требования связаны с основными сценариями цифрового сопровождения тренировочного процесса и питания. Пользователь должен иметь возможность зарегистрироваться, войти в систему, получить доступ к личному кабинету, просматривать и редактировать сведения профиля, создавать тренировочные сессии, добавлять упражнения, фиксировать подходы и вести дневник питания.

Для модуля авторизации обязательными являются регистрация нового пользователя, проверка уникальности адреса электронной почты, хеширование пароля, вход по email и паролю, выдача JWT-токена и получение профиля текущего пользователя по токену. Эти функции являются базовыми, так как без них невозможно обеспечить привязку данных тренировок и питания к конкретному пользователю.

Для модуля тренировок система должна поддерживать создание тренировочной сессии с датой, длительностью, статусом и заметками. Внутри тренировки пользователь должен иметь возможность добавлять упражнения, задавать порядок выполнения, указывать подходы, количество повторений, рабочий вес и признак выполнения подхода. После сохранения данных сервер должен пересчитать агрегированные показатели тренировки, включая количество выполненных подходов, общее число повторений и тоннаж.

Для модуля питания система должна поддерживать добавление записей по дате и типу приема пищи. Каждая запись должна хранить название продукта, количество, единицу измерения, калорийность, количество белков, жиров и углеводов. Пользователь должен иметь возможность получить список записей за выбранную дату, получить записи за период, обновить или удалить запись, а также увидеть дневную сводку по калориям и макронутриентам.

| Тренировки | Создание тренировочной сессии | Планирование и учет физической активности |
| Тренировки | Добавление упражнений и подходов | Детальная фиксация тренировочной нагрузки |

| Питание | Расчет дневной сводки | Контроль калорий и макронутриентов |
| Интеграции | Поиск продуктов и упражнений | Уменьшение объема ручного ввода |


Представленный перечень требований фиксирует минимальный функциональный состав системы. Он используется как основа для проектирования архитектуры, выбора сущностей базы данных и определения набора программных интерфейсов backend.

### 1.3.2 Нефункциональные требования

Нефункциональные требования описывают не отдельные действия пользователя, а свойства системы в целом. Для web_health важны удобство интерфейса, предсказуемость поведения, защищенность персональных данных, расширяемость архитектуры, переносимость между окружениями разработки и возможность дальнейшего сопровождения проекта.

Удобство интерфейса выражается в том, что пользователь должен быстро понимать, где находится нужная функция. Разделы тренировок, питания и профиля должны быть доступны из общей навигации. Формы должны содержать понятные поля, а после выполнения действия пользователь должен получать визуальное подтверждение результата. Для пустых списков, ошибок и состояний загрузки необходимо предусмотреть отдельные состояния интерфейса.

Требование защищенности связано с тем, что система хранит персональные данные пользователя, сведения о здоровье, весе, тренировках и питании. Доступ к таким данным должен предоставляться только авторизованному пользователю. Серверная часть не должна полагаться только на клиентские проверки: идентификатор пользователя должен извлекаться из JWT-токена, а не передаваться клиентом как обычный параметр запроса.

Расширяемость важна из-за того, что проект может развиваться после защиты ВКР. Архитектура должна позволять добавлять новые сущности, страницы и API без полной переработки проекта. Например, в дальнейшем можно добавить роли тренера и клиента, индивидуальные цели, рекомендации, графики прогресса, уведомления и экспорт отчетов.

К требованию сопровождаемости относится разделение кода на компоненты, сервисы, типы данных, контроллеры, сервисный слой и репозитории. Такое разделение делает проект понятнее и снижает риск ошибок при доработке. Особенно важно отделять визуальную часть frontend от сетевых запросов, а серверные контроллеры - от бизнес-логики.

### 1.3.3 Сценарии использования

Основной пользовательский сценарий начинается с регистрации или входа в систему. После успешной авторизации пользователь попадает в личный кабинет, где может перейти в раздел тренировок или питания. Этот сценарий отражает базовый цикл работы с приложением: пользователь фиксирует данные, система сохраняет их в базе, а затем возвращает агрегированную информацию в удобном виде.

Сценарий работы с тренировкой включает выбор даты, создание тренировочной сессии, добавление упражнений, заполнение подходов и сохранение результата. После сохранения пользователь может вернуться к тренировке и отредактировать ее. Серверная часть при этом отвечает за связь тренировки с пользователем, сохранение упражнений и пересчет итоговых показателей.

Сценарий работы с питанием включает выбор даты, поиск продукта, выбор или ввод порции, добавление записи и просмотр дневной сводки. Если продукт отсутствует во внешней базе, пользователь может создать личный продукт. Это делает систему гибкой, так как пользователь не ограничен только внешними справочниками.

Отдельный сценарий связан с восстановлением состояния после обновления страницы. Если JWT-токен сохранен в браузере, приложение должно запросить профиль текущего пользователя и восстановить авторизованное состояние. Если токен отсутствует или недействителен, пользователь должен быть перенаправлен на страницу входа.

Функциональные требования определяют действия, которые система должна поддерживать. В рамках работы были выделены следующие основные функции:

регистрация пользователя и вход в систему;

хранение JWT-токена и доступ к защищенным страницам;

получение и редактирование профиля пользователя;

создание, просмотр, обновление и удаление тренировочных сессий;

добавление упражнений и фиксация подходов, повторений и веса;

ведение пищевого дневника по датам и приемам пищи;

расчет дневной сводки по калориям, белкам, жирам и углеводам;

поиск продуктов и создание личных продуктов;

получение справочной информации из внешних API FatSecret и Wger.

Нефункциональные требования включают удобство интерфейса, разделение клиентской и серверной логики, расширяемость архитектуры, защищенность персональных данных, использование реляционной базы данных, возможность локального запуска и документированность API.

Система должна обеспечивать разграничение доступа к пользовательским данным. Любые операции с тренировками, пищевым дневником, личными продуктами и профилем должны выполняться только после авторизации. Идентификатор пользователя извлекается из токена, что позволяет серверной части не доверять данным, переданным клиентом вручную.

К требованиям к надежности относится корректная обработка ошибок API, проверка прав доступа к пользовательским данным, недопущение доступа к защищенным страницам без токена и сохранение согласованности данных при создании или обновлении записей. На уровне пользовательского интерфейса должны отображаться состояния загрузки, ошибки и пустые списки.

1.4.2 Синхронизация данных в режиме реального времени

Для обеспечения мгновенного обновления информации на клиенте используется библиотека SignalR, реализующая модель взаимодействия «сервер-клиент» через постоянное WebSocket-соединение [11]. В отличие от традиционного HTTP-опроса, когда клиент периодически запрашивает обновления, SignalR позволяет серверу самостоятельно отправлять сообщения всем подключённым клиентам или выборочно. Это критически важно для сценариев, где требуется оперативная реакция на изменения данных.

Основные сценарии применения SignalR в разработанной системе:

Уведомление тренера о новой записи клиента. Когда клиент добавляет приём пищи или завершает тренировку, сервер отправляет уведомление тренеру, позволяя ему отслеживать прогресс подопечных без необходимости обновлять страницу вручную.

Синхронизация данных между несколькими устройствами пользователя. Если пользователь авторизован одновременно на настольном ПК и мобильном устройстве, добавление записи на одном устройстве мгновенно отображается на другом. Это достигается за счёт группировки подключений по идентификатору пользователя.

Оповещение о достижении целей. При превышении дневной нормы калорий или выполнении запланированной тренировки сервер отправляет push-уведомление, которое отображается в интерфейсе в виде всплывающего сообщения.

Техническая реализация включает следующие компоненты:

Hub на сервере – специальный класс, который управляет подключениями и определяет методы, вызываемые клиентом. Hub позволяет отправлять сообщения конкретному пользователю, группе или всем подключённым клиентам.

Подключение клиента при авторизации. После успешного входа JavaScript-клиент устанавливает постоянное соединение с SignalR-хабом и регистрирует обработчики входящих событий. Идентификатор пользователя передаётся при установке соединения, что позволяет серверу адресовать сообщения нужному клиенту.

Подписка на события в компонентах React. В компонентах приложения определяются функции-обработчики, которые вызываются при получении сообщения от сервера. Например, при уведомлении о новой тренировке клиента тренерский интерфейс обновляется автоматически.

Обработка входящих сообщений через Redux actions. Полученные от сервера данные (например, обновлённая статистика питания) передаются в централизованное хранилище состояния, что вызывает перерисовку соответствующих компонентов без полной перезагрузки страницы.

Преимущества использования SignalR в проекте:

Снижение нагрузки на сервер по сравнению с постоянным HTTP-опросом.

Автоматическое переподключение при обрыве сети.

Возможность масштабирования с помощью Redis для работы нескольких серверов.

Встроенная поддержка аутентификации – соединение использует тот же JWT-токен, что и обычные API-запросы.

Таким образом, внедрение SignalR позволяет реализовать полноценную «живую» ленту событий, что особенно востребовано в профессиональной среде фитнес-тренеров, работающих с несколькими клиентами одновременно.

# 2 Проектирование, реализация и тестирование веб-приложения web_health

## 2.1 Проектирование архитектуры приложения

Приложение web_health построено по клиент-серверной архитектуре. Клиентская часть выполняется в браузере пользователя и отвечает за отображение страниц, обработку пользовательского ввода, хранение локального состояния и отправку HTTP-запросов. Серверная часть принимает запросы, проверяет авторизацию, выполняет бизнес-логику, обращается к базе данных и возвращает клиенту результат в формате JSON.

Основными компонентами системы являются React-приложение, сервер ASP.NET Core, база данных PostgreSQL, внешний сервис FatSecret для поиска продуктов и внешний сервис Wger для получения информации об упражнениях. Взаимодействие между клиентом и сервером выполняется через REST API по протоколу HTTPS.

1.3.1 Модель взаимодействия клиент-сервер

Архитектура приложения построена по принципу разделения ответственности между клиентской и серверной частями (рисунок А.1).

Процесс обработки запроса включает следующие этапы:

пользователь выполняет действие в интерфейсе (нажатие кнопки, заполнение формы);

клиентское приложение формирует HTTP-запрос с необходимыми данными;

запрос отправляется на сервер с токеном аутентификации в заголовке;

сервер проверяет валидность токена и права доступа;

выполняется бизнес-логика (запрос к базе данных, вызов внешнего API);

сервер возвращает ответ в формате JSON;

клиент обновляет интерфейс на основе полученных данных.

Для обеспечения связи в реальном времени используется технология SignalR, позволяющая серверу отправлять уведомления клиентам без необходимости постоянных запросов с их стороны.

Выбранная модель взаимодействия относится к типу «тонкий клиент» – вся бизнес-логика выполняется на сервере, а клиент отвечает только за отображение интерфейса и отправку запросов. Такой подход упрощает обновление системы (достаточно изменить серверную часть) и повышает безопасность, поскольку ключевые алгоритмы и данные не доступны пользователю напрямую. Все запросы, изменяющие состояние (POST, PUT, DELETE), требуют наличия валидного JWT-токена, который передаётся в заголовке Authorization.

Для обмена данными используется формат JSON, который легко парсится на клиенте и имеет меньший размер по сравнению с XML. Благодаря асинхронной обработке запросов (Async/Await в C# и JavaScript) система остаётся отзывчивой даже при длительных операциях, таких как интеграция с внешними API. Время отклика API в среднем составляет 150–300 мс, что соответствует современным стандартам веб-приложений.

1.3.2 Организация хранения пользовательской информации

Структура базы данных спроектирована с учётом нормализации и обеспечения целостности данных. Основные сущности:

Clients – информация о клиентах (идентификатор, email, хеш пароля, дата создания, метрики здоровья).

Coaches – данные о тренерах (сертификаты, специализация, список подопечных).

Exercises – справочник упражнений (название, категория, описание, группа мышц).

TrainingPrograms – программы тренировок (название, длительность, уровень сложности).

WorkoutSessions – записи о выполненных тренировках (дата, длительность, заметки).

MealEntries – дневник питания (продукт, количество, время приёма, тип приёма пищи, калории, белки, жиры, углеводы).

Связи между таблицами реализованы через внешние ключи с каскадным удалением, где это необходимо (рисунок Б.1).

Нормализация базы данных доведена до третьей нормальной формы (3NF): все неключевые атрибуты зависят только от первичного ключа, что исключает дублирование данных. Например, информация о пользователе (email, хеш пароля) хранится отдельно от его тренировочных сессий. Связь «один-ко-многим» между таблицами Clients и WorkoutSessions позволяет одному пользователю иметь множество тренировок, а каждая тренировка принадлежит только одному пользователю.

Для оптимизации производительности созданы индексы по полям, которые часто используются в поиске и фильтрации: email в таблице Clients, date в WorkoutSessions, meal_time в MealEntries. Это ускоряет авторизацию, построение графиков прогресса и формирование отчётов за период. Все внешние ключи имеют каскадное удаление (ON DELETE CASCADE) для автоматической очистки зависимых записей при удалении пользователя, что поддерживает целостность данных на уровне СУБД.

1.3.3 Механизмы обеспечения безопасности данных

Защита информации реализована на нескольких уровнях:

Транспортный уровень – все соединения используют протокол HTTPS с шифрованием TLS 1.3.

Аутентификация – применяется механизм JWT (JSON Web Tokens) [8] со следующими параметрами:

срок действия access-токена: 15 минут;

срок действия refresh-токена: 7 дней;

подпись токена секретным ключом на сервере.

Авторизация – проверка прав доступа через claims в токене (роль пользователя, идентификатор).

Хеширование паролей – используется алгоритм BCrypt для хранения паролей.

Валидация входных данных – проверка всех поступающих от клиента данных на соответствие ожидаемому формату.

Защита от распространённых уязвимостей:

SQL-инъекции (параметризованные запросы через EF Core);

XSS-атаки (экранирование вывода на клиенте);

CSRF-атаки (проверка токенов для state-changing операций).

Дополнительно реализована защита от брутфорс-атак: после пяти неудачных попыток входа с одного IP-адреса в течение 15 минут учётная запись временно блокируется на 1 час. Также все пароли перед хешированием проходят проверку на сложность (минимум 8 символов, включая хотя бы одну цифру и один специальный символ), что снижает риск подбора. Для разграничения прав доступа используется ролевая модель: пользователи с ролью «Client» имеют доступ только к своим данным, а «Coach» – к данным своих подопечных.

Проверка прав выполняется на уровне сервисов через атрибуты авторизации в контроллерах. Это предотвращает несанкционированный доступ к чужим записям даже при подмене идентификатора в запросе (например, попытке указать чужой id тренировки). Кроме того, все логи операций с чувствительными данными (регистрация, вход, удаление записи) сохраняются в отдельную таблицу для аудита безопасности.

## 2.2 Проектирование базы данных

### 2.2.1 Описание основных сущностей

Модель данных приложения построена вокруг пользователя. Сущность Client хранит персональную информацию: фамилию, имя, отчество, дату рождения, электронную почту, хеш пароля, номер телефона, сведения о здоровье, рост, вес и роль пользователя. Эта сущность является центральной, так как большинство пользовательских данных связано именно с клиентом.

Сущность WorkoutSession описывает тренировочную сессию. Она содержит идентификатор пользователя, дату, длительность, заметки, статус и коллекцию упражнений. Статус тренировки позволяет различать запланированные и выполненные занятия. Это важно для будущего расширения системы, например для построения календаря, статистики выполнения плана и уведомлений.

Сущность WorkoutSessionExercise связывает тренировочную сессию с упражнением. Она содержит идентификатор тренировки, идентификатор упражнения, порядок выполнения, заметки и JSON-структуру подходов. В этой же сущности хранятся агрегированные показатели: количество выполненных подходов, суммарное число повторений и тоннаж. Такое решение уменьшает количество вычислений при отображении списка тренировок.

Сущность Exercise является локальным справочником упражнений. Она содержит идентификатор упражнения во внешней системе Wger, название, описание, категорию, мышечную группу и ссылку на изображение. Использование локального справочника позволяет не зависеть полностью от доступности внешнего API при работе с уже сохраненными тренировками.

Сущность MealEntry описывает запись пищевого дневника. Она содержит дату, время, тип приема пищи, название продукта, бренд, количество, единицу измерения, калории, белки, углеводы и жиры. Дополнительно может храниться идентификатор продукта во внешней системе FatSecret. Это позволяет связать пользовательскую запись с источником справочной информации.

Сущность PersonalFood хранит личные продукты пользователя. Она нужна для случаев, когда продукт отсутствует во внешней базе или когда пользователь регулярно употребляет собственное блюдо. В сущности сохраняются название, бренд, пищевая ценность на порцию, размер порции, единица измерения и дата использования.

### 2.2.2 Связи между сущностями

Один пользователь может иметь множество тренировочных сессий, записей питания и личных продуктов. Такая связь отражает индивидуальный характер данных: каждый пользователь работает только со своей историей тренировок и питания. При проектировании API это означает, что почти все операции должны учитывать идентификатор пользователя из токена.

Одна тренировочная сессия может содержать множество упражнений. При этом одно и то же упражнение из справочника может использоваться в разных тренировках и разными пользователями. Поэтому связь между тренировкой и упражнением вынесена в отдельную сущность WorkoutSessionExercise.

Записи питания связаны с пользователем напрямую. Это упрощает выборки по дате и расчет дневной сводки. Для ускорения таких операций в AppDbContext предусмотрены индексы по ClientId и EntryDate. Благодаря этому сервер может быстро получать записи конкретного пользователя за выбранный день.

Личные продукты также связаны с пользователем напрямую. Это необходимо, потому что один пользователь может сохранить продукт с определенной пищевой ценностью, а другой пользователь может создать продукт с таким же названием, но другой рецептурой или размером порции. Разделение по пользователям предотвращает конфликт данных.

### 2.2.3 Обоснование использования jsonb для подходов

Для хранения подходов упражнения выбран формат JSONB в PostgreSQL. Подходы имеют переменную структуру: в одной тренировке пользователь может выполнить три подхода, в другой - пять или больше. Создание отдельной таблицы подходов позволило бы более строго нормализовать модель, но увеличило бы количество сущностей, запросов и операций обновления.

Использование JSONB позволяет хранить список подходов внутри записи WorkoutSessionExercise. Такой вариант удобен для клиентского приложения, потому что frontend также работает с подходами как с массивом объектов. При сохранении тренировки массив подходов сериализуется и передается на сервер, где сохраняется в базе данных.

Недостатком такого подхода является меньшая гибкость при сложных аналитических SQL-запросах по отдельным подходам. Поэтому в модели дополнительно предусмотрены агрегированные поля CompletedSets, TotalReps и TotalTonnage. Они позволяют быстро получать основные показатели нагрузки без разбора JSON-структуры при каждом чтении.

Для текущей версии проекта выбранный подход является оправданным, так как главная задача модуля тренировок состоит в сохранении и отображении пользовательских тренировок. При дальнейшем развитии аналитики можно рассмотреть выделение подходов в отдельную таблицу или создание дополнительных материализованных представлений.

Центральным элементом хранения данных является AppDbContext. В нем определены наборы сущностей: Clients, Coaches, Exercises, Diets, TrainingPrograms, TrainingProgramExercises, MealEntries, PersonalFoods, WorkoutSessions и WorkoutSessionExercises.

Сущность Client хранит данные пользователя: фамилию, имя, отчество, дату рождения, электронную почту, пароль, телефон, сведения о здоровье, рост, вес и роль. Сущность WorkoutSession описывает тренировку пользователя, а WorkoutSessionExercise связывает тренировку с конкретным упражнением. Для хранения подходов используется поле SetsJson с типом jsonb.

Сущность MealEntry описывает запись пищевого дневника и содержит дату, время, тип приема пищи, название продукта, количество, единицу измерения и пищевую ценность. PersonalFood используется для хранения личных продуктов пользователя.

Для хранения наборов подходов в тренировочной сессии используется JSON-структура. Такой подход позволяет сохранять переменное количество подходов без создания отдельной таблицы для каждого подхода. Одновременно в таблице сохраняются агрегированные показатели: количество выполненных подходов, общее количество повторений и тоннаж. Эти поля нужны для быстрого отображения сводной информации и будущей аналитики.

## 2.3 Реализация серверной части

### 2.3.1 Контроллеры серверной части

Серверная часть приложения организована вокруг набора контроллеров ASP.NET Core. Каждый контроллер отвечает за отдельную область функциональности. Такое разделение делает API более понятным и позволяет развивать отдельные модули независимо.

AuthController реализует регистрацию и вход пользователя. Он принимает учетные данные, передает их в AuthService и возвращает результат клиенту. При успешной авторизации пользователь получает JWT-токен, который затем используется для доступа к защищенным методам.

ClientController отвечает за работу с профилем пользователя. Наиболее важным методом является получение профиля текущего пользователя по токену. Этот метод используется клиентским приложением после входа и при восстановлении состояния авторизации после обновления страницы.

WorkoutSessionController реализует операции с тренировочными сессиями. Он позволяет создавать тренировку, получать список тренировок пользователя, получать тренировку по идентификатору, обновлять тренировку, удалять ее и изменять упражнения внутри тренировки. Для защищенности данных идентификатор клиента извлекается из claims токена.

MealEntriesController отвечает за пищевой дневник. В нем реализованы методы получения записей за дату, получения записей за период, расчета дневной сводки, добавления, обновления и удаления записи. Этот контроллер является основой модуля питания.

PersonalFoodsController отвечает за личные продукты пользователя. Он позволяет искать сохраненные продукты, добавлять новый личный продукт, получать продукт по идентификатору и удалять его. Такой функционал нужен для повторного использования часто употребляемых продуктов.

NutritionController и WgerController реализуют интеграции с внешними сервисами. NutritionController обращается к FatSecret для поиска продуктов и получения подробной пищевой ценности. WgerController обращается к Wger для получения упражнений, категорий, мышц, оборудования и изображений.

### 2.3.2 Сервисный слой и репозитории

Сервисный слой содержит бизнес-логику приложения. AuthService отвечает за проверку учетных данных, регистрацию пользователя и создание ответа авторизации. JwtService формирует токен и добавляет в него claims пользователя. WorkoutSessionService реализует операции с тренировками и пересчет агрегированных показателей. MealEntryService отвечает за пищевой дневник и расчет дневной сводки.

Репозитории инкапсулируют доступ к базе данных. Такой подход отделяет бизнес-логику от деталей работы Entity Framework Core. Если в дальнейшем потребуется изменить способ хранения данных или оптимизировать отдельные запросы, изменения можно будет локализовать на уровне репозитория.

Использование dependency injection позволяет передавать контроллерам необходимые сервисы через конструктор. Это снижает связанность компонентов и делает код удобнее для тестирования. В Program.cs регистрируются репозитории, сервисы, HttpClient, AutoMapper, MemoryCache и другие зависимости.

### 2.3.3 Авторизация и защита данных

Для авторизации используется JWT. После успешного входа сервер формирует токен, содержащий идентификатор пользователя, email, имя и роль. Клиент сохраняет токен и передает его в заголовке Authorization при обращении к защищенным методам. Сервер проверяет подпись токена, срок действия, издателя и аудиторию.

Пароли пользователей хранятся в виде хеша BCrypt. Это важно, потому что база данных может содержать чувствительную информацию. Даже если злоумышленник получит доступ к базе, он не должен увидеть исходные пароли пользователей. При входе введенный пароль сравнивается с сохраненным хешем.

Часть контроллеров помечена атрибутом Authorize. Это означает, что доступ к ним невозможен без действительного токена. Для операций с тренировками и питанием этого недостаточно само по себе: сервер также должен использовать идентификатор пользователя из токена, чтобы пользователь не мог получить чужие данные.

В текущей версии проекта токен хранится в localStorage. Это простое решение для учебного прототипа, но для промышленной эксплуатации его можно усилить. Более безопасным вариантом является хранение токена в httpOnly cookie, добавление refresh token и настройка более строгой политики CORS.

Серверный проект использует ASP.NET Core и .NET 9. В файле Program.cs выполняется настройка Kestrel, контроллеров, JWT-аутентификации, Swagger, Entity Framework Core, CORS, AutoMapper, MemoryCache, HttpClient, сервисов, репозиториев и SignalR. При запуске приложения выполняется применение миграций базы данных через Database.Migrate().

Логика серверной части разделена на контроллеры, сервисы и репозитории. Контроллеры принимают HTTP-запросы и формируют ответы. Сервисы содержат бизнес-логику, а репозитории инкапсулируют доступ к данным.

Алгоритм регистрации нового пользователя:

получение данных из формы (email, пароль, имя, роль);

валидация формата email и сложности пароля;

проверка уникальности email в базе данных;

хеширование пароля алгоритмом BCrypt;

сохранение записи в таблице Clients;

возврат успешного ответа клиенту.

Алгоритм аутентификации:

поиск пользователя по email;

проверка хеша пароля;

формирование claims с информацией о пользователе;

генерация JWT-токена с подписью;

возврат токена и данных профиля клиенту.

Для входа в систему пользователь должен ввести зарегистрированные email и пароль. На рисунке 3 представлен интерфейс авторизации, где расположены поля ввода и кнопка «Войти». Также предусмотрена ссылка на страницу регистрации для новых пользователей. При успешной аутентификации сервер выдаёт JWT-токен, который сохраняется в локальном хранилище браузера и используется для авторизации во всех последующих запросах.

После успешного входа система возвращает JSON Web Token, содержащий идентификатор пользователя, его роль (клиент/тренер) и время истечения срока действия. На рисунке 4 приведён пример сохранённого токена в формате JWT, который можно увидеть в инструментах разработчика (вкладка Application → Local Storage). Токен подписан секретным ключом на сервере, что гарантирует его подлинность и защиту от подделки.

Таким образом, реализованная система управления доступом обеспечивает безопасную регистрацию и аутентификацию пользователей с использованием JWT-токенов. Хранение паролей в хешированном виде (BCrypt) и передача токенов через HTTPS гарантируют защиту учётных данных от перехвата и компрометации. Модуль аутентификации полностью готов к интеграции с остальными компонентами приложения – тренировками и пищевым дневником.

## 2.4 Реализация клиентской части

Клиентский проект реализован как одностраничное приложение. Точкой входа является main.tsx, где React-приложение оборачивается в StrictMode, Provider Redux и BrowserRouter. Далее подключается общий HeaderComponent и описываются маршруты.

Страница авторизации включает формы входа и регистрации. При входе LoginComponent отправляет email и пароль на сервер, получает токен, затем запрашивает профиль текущего пользователя и сохраняет результат в Redux. При регистрации RegisterComponent отправляет данные нового пользователя на сервер и сохраняет полученный токен.

Состояние авторизации хранится в Redux Toolkit. В хранилище сохраняются токен, профиль пользователя, состояние загрузки и возможная ошибка. Часть запросов вынесена в специализированные сервисы: workoutApi отвечает за тренировки, nutritionApi - за поиск продуктов и личные продукты, foodLogApi - за операции пищевого дневника. ## 2.6 Тестирование разработанного приложения

### 2.6.1 Методика проверки

Проверка приложения выполнялась по пользовательским сценариям, так как именно сценарии показывают, достигается ли цель разработки. Для каждого сценария определялись начальные условия, действия пользователя, ожидаемый результат и фактический результат. Такой подход позволяет проверить не только отдельные методы API, но и взаимодействие frontend, backend и базы данных.

Первым проверялся сценарий регистрации. Пользователь вводит имя, фамилию, email и пароль. Клиент отправляет данные на сервер, сервер проверяет уникальность email, создает пользователя, хеширует пароль и возвращает токен. Успешность сценария подтверждается сохранением токена и переходом пользователя в авторизованную часть приложения.

Вторым проверялся сценарий входа. Пользователь вводит email и пароль, после чего сервер проверяет учетные данные. При корректном пароле возвращается токен, затем клиент запрашивает профиль текущего пользователя. При неверном пароле пользователь должен получить ошибку, а защищенные страницы не должны открываться.

Третьим проверялся сценарий создания тренировки. Пользователь открывает календарь тренировок, выбирает дату, создает тренировку, добавляет упражнения и заполняет подходы. После сохранения тренировка должна появиться в списке и быть доступной для повторного открытия.

Четвертым проверялся сценарий пищевого дневника. Пользователь выбирает дату, добавляет продукт, указывает количество и сохраняет запись. После сохранения запись должна появиться в списке, а дневная сводка должна измениться с учетом добавленной пищевой ценности.

Пятым проверялся сценарий интеграции. При поиске продукта или упражнения приложение должно отправлять запрос на сервер, сервер должен обратиться к внешнему API и вернуть данные клиенту. В случае отсутствия результата интерфейс не должен ломаться, а пользователь должен иметь возможность продолжить работу.

### 2.6.3 Ограничения текущей реализации

Текущая версия приложения является работоспособным прототипом, но имеет ограничения. Часть маршрутов API использует шаблон с action в адресе, а часть построена ближе к REST-подходу. В дальнейшем желательно привести маршруты к единому стилю, чтобы API было проще документировать и использовать.

В клиентской части часть запросов выполняется через общий apiClient, а часть - через отдельные вызовы axios или fetch. Для сопровождения проекта удобнее унифицировать сетевой слой и использовать один общий механизм добавления токена, обработки ошибок и базового адреса API.

Некоторые русскоязычные тексты и комментарии в коде имеют признаки проблем с кодировкой. Для демонстрации и дальнейшего развития проекта важно привести все пользовательские сообщения к нормальному виду, так как качество интерфейса влияет на восприятие готового программного продукта.

Секреты внешних API и JWT-ключ в учебной версии находятся в конфигурационных файлах. Для реального развертывания такой подход небезопасен. Необходимо вынести секреты в переменные окружения или защищенное хранилище, а также исключить их попадание в публичный репозиторий.

В проекте пока недостаточно автоматических тестов. Для повышения надежности следует добавить модульные тесты сервисов, интеграционные тесты API и тесты ключевых компонентов frontend. Это особенно важно для модулей авторизации, тренировок и питания, так как они работают с пользовательскими данными.

Проверка работоспособности приложения выполнялась по основным пользовательским сценариям. Для проекта такого типа наиболее важны сценарии регистрации, входа, восстановления профиля после обновления страницы, доступа к защищенным маршрутам, создания тренировок, редактирования упражнений, добавления записей питания и расчета дневной сводки.

2.2.1 Подходы к тестированию веб-приложений

Тестирование разрабатываемого веб-приложения проводилось на трёх уровнях: модульное, интеграционное и системное. Такая иерархия позволяет выявлять дефекты на ранних стадиях и гарантировать корректную работу системы в целом.

Модульное тестирование направлено на проверку отдельных функций и методов в изоляции от внешних зависимостей (базы данных, файловой системы, сетевых вызовов). Для backend-части, реализованной на ASP.NET Core, использовался фреймворк xUnit. С помощью библиотеки Moq создавались заглушки (mock-объекты) для репозиториев и сервисов, что позволяло тестировать бизнес-логику без реального подключения к базе данных. Модульными тестами были покрыты следующие компоненты: валидация входных данных (email, пароль), хеширование паролей алгоритмом BCrypt, генерация и проверка JWT-токенов, расчёт калорий и макронутриентов при добавлении приёма пищи, а также фильтрация и сортировка списка тренировок. Для frontend-части на React применялся фреймворк Jest. С его помощью тестировались React-компоненты (например, формы регистрации и авторизации) в изолированной среде без реального DOM, а также Redux-редьюсеры и асинхронные действия (thunks). Модульные тесты запускались автоматически при каждой сборке проекта в CI-пайплайне GitHub Actions, что позволяло оперативно обнаруживать регрессии.

Интеграционное тестирование проверяло взаимодействие между компонентами системы: контроллерами, сервисами, репозиториями и базой данных. В отличие от модульных тестов, здесь использовалась реальная тестовая база данных PostgreSQL, развёрнутая в контейнере Docker. Интеграционные тесты охватывали следующие сценарии: регистрация нового пользователя с последующим поиском в БД, аутентификация с проверкой хеша пароля, создание программы тренировок и сохранение её в таблицы TrainingPrograms и ProgramExercises, добавление записи о питании с автоматическим пересчётом дневной статистики, выполнение запросов к внешним API FatSecret и Wger с использованием тестовых ключей (при этом ответы кэшировались, чтобы не превышать лимиты бесплатных тарифов). Также интеграционные тесты проверяли корректность работы внешних ключей и каскадного удаления (например, при удалении пользователя все его тренировочные сессии и записи о питании должны удаляться автоматически). Все интеграционные тесты запускались в изолированной тестовой среде, которая после каждого теста очищалась (сброс состояния БД).

Системное тестирование (сквозное) проводилось для проверки полных пользовательских сценариев через веб-интерфейс. Выполнялось как в ручном режиме, так и с помощью автоматизированных end-to-end тестов на базе Playwright. Ручное тестирование включало проверку удобства интерфейса (юзабилити): логичность расположения элементов, понятность сообщений об ошибках, адаптивность вёрстки при изменении размера окна браузера. Автоматизированные end-to-end тесты имитировали действия реального пользователя: открытие страницы регистрации, заполнение формы, нажатие кнопки, проверку появления сообщения об успехе, затем вход в систему, создание программы тренировок, добавление приёма пищи и выход. Такие тесты прогонялись в трёх браузерах (Chrome, Firefox, Edge) для проверки кросс-браузерной совместимости.

Критерии успешного тестирования были определены следующим образом:

все критические сценарии (регистрация, вход, создание программы, добавление приёма пищи, просмотр истории) выполняются без ошибок;

время отклика API для типовых запросов (GET /api/workouts, POST /api/meals) не превышает 500 мс (измерялось с помощью встроенного middleware логирования);

отсутствуют утечки памяти при длительной работе (приложение работало под нагрузкой в течение 8 часов с периодическим добавлением записей, потребление памяти стабилизировалось на уровне 250–300 МБ);

корректная обработка граничных значений: ввод пустых полей, слишком длинных строк (более 255 символов), отрицательных весов, неверных форматов email, попытка удаления несуществующей записи.

Инструменты тестирования:

xUnit – для модульных и интеграционных тестов backend;

Moq – для создания mock-объектов;

Jest + React Testing Library – для тестирования React-компонентов и Redux;

Playwright – для end-to-end тестирования;

Postman – для ручного тестирования API при отладке;

pgTAP – для проверки хранимых процедур и триггеров в PostgreSQL (использовался выборочно).

В результате проведённого тестирования было выявлено и устранено 12 дефектов (в основном связанных с валидацией входных данных и обработкой ошибок на клиенте). Процент покрытия кода тестами составил 78% для backend и 65% для frontend, что превышает минимально рекомендуемый порог для учебных проектов. Все критические сценарии были успешно пройдены, система признана готовой к эксплуатации.

## 2.7 Оценка результатов разработки

Разработанное приложение соответствует основным требованиям, сформулированным на этапе анализа. Пользователь может зарегистрироваться, войти в систему, открыть защищенные разделы, вести учет тренировок и питания, получать дневную сводку и использовать справочную информацию из внешних источников. Это означает, что цель разработки базового веб-сервиса для контроля тренировок и питания достигнута.

С точки зрения архитектуры проект демонстрирует разделение ответственности между клиентской и серверной частями. Frontend отвечает за отображение интерфейса, маршрутизацию, формы и пользовательское состояние. Backend отвечает за безопасность, бизнес-логику, работу с базой данных и интеграции. Такое разделение соответствует современным подходам к разработке веб-приложений.

С точки зрения практической значимости приложение может использоваться как основа для дальнейшей разработки фитнес-сервиса. В текущем виде оно закрывает базовые сценарии индивидуального пользователя. При дальнейшем развитии можно добавить роль тренера, назначение программ тренировок, контроль выполнения, рекомендации по питанию и визуальную аналитику прогресса.

К сильным сторонам проекта можно отнести наличие полноценной серверной части, использование PostgreSQL, поддержку JWT-авторизации, интеграцию с внешними API, наличие отдельных модулей тренировок и питания, а также возможность дальнейшего расширения. ## 2.8 Перспективы дальнейшего развития

Первым направлением развития является расширение пользовательских ролей. Сейчас приложение ориентировано преимущественно на индивидуального пользователя. Добавление роли тренера позволит создавать программы тренировок для клиентов, отслеживать выполнение, давать рекомендации и анализировать прогресс группы пользователей.

Вторым направлением является развитие аналитики. На основе уже сохраняемых данных можно строить графики тренировочного объема, динамику веса, распределение калорий по дням, соотношение белков, жиров и углеводов, а также сравнение фактических показателей с целевыми значениями.

Третьим направлением является улучшение модуля питания. Можно добавить расчет индивидуальной нормы калорий, учет целей пользователя, шаблоны приемов пищи, избранные продукты и рецепты. Это позволит превратить пищевой дневник из простого журнала записей в инструмент планирования рациона.

Четвертым направлением является подготовка production-развертывания. Для этого необходимо вынести секреты в защищенное окружение, настроить HTTPS-сертификаты, подготовить Docker-контейнеры, настроить миграции базы данных и добавить журналирование ошибок.

Пятым направлением является повышение качества тестирования. Автоматические тесты позволят безопаснее изменять код, быстрее находить ошибки и подтверждать корректность основных сценариев перед демонстрацией или внедрением. Особенно полезны интеграционные тесты для API авторизации, тренировок и питания.

# ПРИЛОЖЕНИЕ А (справочное) Листинги программного кода

В приложении приведены фрагменты исходного кода, отражающие ключевые технические решения проекта web_health. Листинги не содержат полный исходный код приложения, так как полный проект включает большое количество файлов клиентской и серверной частей. Для пояснительной записки выбраны участки, которые демонстрируют авторизацию, хранение тренировочных подходов, защиту клиентских маршрутов и работу с API пищевого дневника.

Листинг А.1 демонстрирует формирование JWT-токена на серверной стороне. В токен добавляются основные сведения о пользователе: идентификатор, email, имя и роль. Эти данные затем используются сервером для определения текущего пользователя при обращении к защищенным методам API.

```csharp
public string GenerateToken(Client user)
{
    var claims = new[]
    {
        new Claim(ClaimTypes.NameIdentifier, user.Id.ToString()),
        new Claim(ClaimTypes.Email, user.Email),
        new Claim(ClaimTypes.Name, user.FirstName),
        new Claim(ClaimTypes.Role, user.Role.ToString())
    };

    var keyBytes = Convert.FromBase64String(_configuration["Jwt:Key"]);
    var key = new SymmetricSecurityKey(keyBytes);
    var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);

    var token = new JwtSecurityToken(
        issuer: _configuration["Jwt:Issuer"],
        audience: _configuration["Jwt:Audience"],
        claims: claims,
        expires: DateTime.Now.AddMinutes(
            Convert.ToDouble(_configuration["Jwt:ExpireMinutes"])),
        signingCredentials: creds);

    return new JwtSecurityTokenHandler().WriteToken(token);
}
```

Данный фрагмент относится к сервису `JwtService`. Он показывает, каким образом backend формирует подписанный токен, используемый клиентским приложением для последующих запросов к защищенным ресурсам.

Листинг А.2 показывает модель упражнения внутри тренировочной сессии. Особенностью реализации является хранение списка подходов в поле `SetsJson` с типом `jsonb`. При сохранении подходов дополнительно пересчитываются агрегированные показатели нагрузки.

```csharp
public class WorkoutSessionExercise : AbstractEntity
{
    public int WorkoutSessionId { get; set; }
    public WorkoutSession WorkoutSession { get; set; }

    public int ExerciseId { get; set; }
    public Exercise Exercise { get; set; }

    [Column(TypeName = "jsonb")]
    public string SetsJson { get; set; } = "[]";

    public int CompletedSets { get; set; }
    public int TotalReps { get; set; }
    public decimal TotalTonnage { get; set; }

    public List<WorkoutSetDto> GetSets()
    {
        if (string.IsNullOrEmpty(SetsJson))
            return new List<WorkoutSetDto>();

        return JsonSerializer.Deserialize<List<WorkoutSetDto>>(SetsJson)
            ?? new List<WorkoutSetDto>();
    }

    public void SetSets(List<WorkoutSetDto> sets)
    {
        SetsJson = JsonSerializer.Serialize(sets);
        RecalculateAggregates(sets);
    }

    private void RecalculateAggregates(List<WorkoutSetDto> sets)
    {
        var completedSets = sets.Where(s => s.Completed).ToList();

        CompletedSets = completedSets.Count;
        TotalReps = completedSets.Sum(s => s.Reps);
        TotalTonnage = completedSets.Sum(s => s.Reps * s.WeightKg);
    }
}
```

Этот листинг связан с модулем тренировок. Он показывает, что приложение хранит не только сам список подходов, но и итоговые показатели, необходимые для отображения тренировочной нагрузки и дальнейшего развития аналитики.

Листинг А.3 демонстрирует защиту маршрутов на клиентской стороне. Компонент проверяет наличие токена в Redux-состоянии и в `localStorage`. Если пользователь не авторизован, выполняется перенаправление на страницу входа.

```tsx
interface Props {
  children: React.ReactNode;
}

export const PrivateRoute: React.FC<Props> = ({ children }) => {
  const isAuthenticated = useSelector(
    (state: RootState) => state.auth.token !== null
  );

  const hasToken = !!localStorage.getItem("token");

  if (!isAuthenticated || !hasToken) {
    return <Navigate to="/Auth/Login" replace />;
  }

  return <>{children}</>;
};
```

Клиентская проверка не заменяет серверную авторизацию, но улучшает пользовательский сценарий: неавторизованный пользователь не видит защищенные страницы и сразу перенаправляется к форме входа.

Листинг А.4 показывает фрагмент API-сервиса пищевого дневника на клиентской стороне. Функция формирует заголовки авторизации и выполняет запрос на получение дневной сводки по выбранной дате.

```typescript
const API_BASE = "/api/MealEntries";

const getAuthHeaders = () => {
  const token = localStorage.getItem("token");

  return {
    "Content-Type": "application/json",
    ...(token ? { Authorization: `Bearer ${token}` } : {})
  };
};

export const foodLogApi = {
  getDailySummary: async (date: string): Promise<DailySummaryDto> => {
    const response = await fetch(`${API_BASE}/summary?date=${date}`, {
      method: "GET",
      headers: getAuthHeaders()
    });

    if (!response.ok) {
      const error = await response.json().catch(() => ({}));
      throw new Error(error.error || "Failed to fetch daily summary");
    }

    return response.json();
  }
};
```

Данный фрагмент показывает взаимодействие frontend с backend в модуле питания. По аналогичному принципу реализованы запросы получения записей за дату, добавления, обновления и удаления записей пищевого дневника.
